# Acceptance Criteria Rules (shared)
# Referenced by all Seek phase skills during self-validation.
# Adapted from GuideTree — keeps the same standard for verifiability.

## Invalid Vague Phrases

The following phrases are invalid as standalone acceptance criteria because a third party cannot judge whether they are satisfied:

English:
- good experience / better performance / high quality
- works well / reasonable result / reasonable solution
- optimized / improved / improved results
- user friendly / handles well

Chinese:
- 效果好 / 体验好 / 体验不错 / 高质量
- 性能好 / 合理 / 优化 / 完善 / 好用

These phrases are allowed only when paired with concrete evidence, threshold, artifact, metric, approval condition, or observable behavior.

## Valid Criteria Pattern

A valid acceptance criterion must be verifiable by inspection, review, test, approval, or measurable evidence. A third party must be able to judge whether the criterion is satisfied.

### Good examples
- "The requirements document contains target users, core scenarios, MVP scope, non-goals, and success metrics."
- "The prototype demonstrates the three core user flows defined in the requirements phase."
- "The release candidate passes the defined functional, security, and deployment checks."
- "Each target user scenario is documented in a table containing actor, trigger, input, expected outcome, priority, and source."

### Bad examples
- "The project is going well."
- "The design is reasonable."
- "The user experience is good."
- "The system is optimized."
- "The team is satisfied."

## Weak Verbs Requiring Concrete Scope

These verbs are weak on their own but acceptable when paired with a concrete object, metric, threshold, or completion evidence:

- improve / optimize / enhance / refine
- handle / process / manage / support
- update / review / analyze / research
- design / test / implement
